# Disaster Recovery Runbook

If the automated deployment fails at any stage AFTER a database migration or IF the production database becomes corrupted, follow this runbook. DO NOT attempt automated recovery.

## Pre-requisites
- Ensure you have the `pg_restore` and `psql` tools available.
- Locate the most recent verified database backup file (`.dump`) generated by the deployment script.

## Scenario 1: Migration Applied but Application Health Check Failed
1. **Analyze the Failure**: Review the application logs (`journalctl -u exam-portal.service`) to identify why the application failed to start or serve requests.
2. **Determine Fix Strategy**:
   - If the application code is buggy but the database schema is sound, author a new commit with the fix, push to `main`, and run the deployment again.
   - If the database schema is incorrect, author a NEW Alembic migration that corrects the schema, push, and deploy.
3. **DO NOT**: Do not run `flask db downgrade`.

## Scenario 2: Severe Data Corruption (Requires Restore)
1. **Stop Application**: Stop the application service to prevent further data changes.
   ```bash
   sudo systemctl stop exam-portal.service
   ```
2. **Verify Backup**: Locate the last good backup in the backup directory and verify it using `pg_restore --list <backup_file.dump>`.
3. **Restore Database**: (Proceed with extreme caution. This requires human approval and may lead to data loss of recent transactions).
   - Terminate connections.
   - Drop the current database and recreate it.
   - Restore using `pg_restore -d <database_name> <backup_file.dump>`.
4. **Restart Application**:
   ```bash
   sudo systemctl start exam-portal.service
   ```
